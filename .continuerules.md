# AffinityLog Architecture

## Project context
Portfolio backend for Amazon Bio Discovery (AWS antibody engineering platform) CSV exports.
No public API exists for Bio Discovery as of June 2026 — UI-only, CSV export is the only
integration point. Do not suggest API/SDK calls to Bio Discovery; none exist.

## Stack
- FastAPI + Strawberry GraphQL + async SQLAlchemy 2.0 + asyncpg + PostgreSQL 16
- REST only for multipart file upload (`/experiments`, `/experiments/{id}/candidates/import`)
- GraphQL (`/graphql`) for all queries, filtering, sorting, comparison, mutations
- Alembic for migrations. Testcontainers (postgres:16-alpine) for integration tests — never mock the DB layer
- ruff + black (line-length 100) + mypy strict

## SQLAlchemy 2.0 conventions (see orm.py `Module` class as the canonical reference)
- `Mapped[type]` with `mapped_column()`, never legacy `Column()` for typed columns
- UUID PKs: `Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)`
- Nullable is `Mapped[type | None]`, not `Optional[type]`
- String columns get explicit length: `mapped_column(String(255))`
- `created_at`: `mapped_column(DateTime(timezone=True), server_default=func.now())`
- JSONB for variable/recipe-specific data, GIN-indexed when queried into:
  `Index("ix_candidates_scores_gin", "scores", postgresql_using="gin")`
- Composite uniqueness with NULL handling: use `postgresql_nulls_not_distinct=True` on
  `UniqueConstraint` when NULL should count as a collision, not an exception
- Relationships are nav properties, not columns — `relationship(back_populates=...)`,
  `cascade="all, delete-orphan"` on the owning side of a composition
- Comment the raw SQL equivalent inline wherever the ORM does something Postgres-specific
  (this project's stated convention — ORM as convenience, not black box)

## Data model philosophy
- Catalog side (Module, Metric, Concept, Recipe) is seeded reference data
- Experiment side (Project, Target, Experiment, Candidate, Artifact) is ingested data
- Only stable, cross-recipe metrics get dedicated indexed columns
- Everything variable goes in JSONB (`Candidate.scores`, `Metric.transform`), exposed via
  GraphQL's JSON scalar — avoids schema migrations when a new recipe emits new columns
- `Metric` identity is `(module_id, column_key, variant_kind, variant)`, not column_key alone —
  the same column name can mean different things across modules/runs

## Session layer
- Session-per-request: GraphQL context passes the engine, not a session — each resolver
  opens its own session via `get_session()`. Avoids session-lifetime issues across resolvers.
- `expire_on_commit=False` — ORM objects stay readable after commit when handed to the API layer

## Strawberry GraphQL
- Resolvers stay thin — business logic in service/model layer
- Mutations return the mutated entity
- camelCase in GraphQL schema, snake_case in Python (Strawberry's default conversion)

Concurrency

One lock per invariant

One request shares one AsyncSession across the whole resolver tree. graphql-core gathers sibling fields, and SQLAlchemy's own docstring says an AsyncSession isn't safe for use in concurrent tasks.

the session lock

Lives privately inside TaskSafeSession. Nothing else can hold it, because nothing else can reach the session.

_catalog_lock

Held across the whole catalog build, which issues its own statement. That's safe only because the statement takes a different lock.

_interface_kinds_lock

The same shape again, for the per-request map of candidate to interface kind.

asyncio.Lock isn't reentrant, so one lock serving two invariants deadlocks. The task waits on itself forever, with no exception, no traceback and no timeout, while every other request on the loop is served normally. There are tests that collapse each memo lock back into the session's and assert the hang.
